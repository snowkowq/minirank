MiniRank — Project Process Report

Documentation of the build process, prompts, and retrospective for the MiniRank keyword-tracking project.

"This project was developed using an AI coding assistant (opencode) for code generation and a separate AI chat for brainstorming and structuring, in accordance with the brief's requirements."

Section 1 — Plan

a) Stack choice

Plain PHP, no framework. Free models have small context windows; a large scaffold would waste it. SQLite gives zero setup for the evaluator and satisfies the "runs in 5 minutes" requirement. Every line in the repository is code I can explain.

b) Build order

Schema, then seed, then repository, then read pages, then CRUD, then AJAX, then CSS. Foundation first, because a schema mistake propagates everywhere.

c) Design decisions made by me, not the agent

  • The UNIQUE(keyword_id, tracked_on) constraint, requested on day one, which turned out to solve the Refresh idempotency three days later.
  • The 3-position threshold for the trend.
  • The TrendCalculator, written by hand.
  • Starting position 30–70 in the seed instead of 1–100, for more plausible demo data.

d) AGENTS.md used as a working instrument, not a formality

It contained prescriptive rules: wrong/right SQL examples, escaping required inside HTML attributes, and "modify only the requested files". I then used it as the review standard that caught the agent's own deviations from it.

e) Architecture retrospective

The trend rule was ambiguously phrased in my AGENTS.md ("or the oldest available in the window"), which produced two divergent implementations in the code.

Section 2 — Prompts & Fixes

1. The prompt that failed (full CRUD in one go)

Prompt

Read AGENTS.md. Existing: public/index.php (autoloader, `page` routing, trendLabel() helper), src/KeywordRepository.php, views/keywords_list.php, views/keyword_detail.php. Add keyword CRUD (single user, no login): 1. src/KeywordRepository.php — add: - create(string $phrase): int - update(int $id, string $phrase): bool - delete(int $id): bool 2. public/index.php — handle POST actions: create, update, delete. Validate: phrase is required, trimmed, max 200 chars. The phrase is UNIQUE COLLATE NOCASE — catch the constraint violation and show a readable error instead of a PDO exception. After a successful POST, redirect back to the list (POST/Redirect/GET) so a refresh does not resubmit. 3. views/keywords_list.php — add an "Add keyword" form, plus edit and delete controls per row. Delete must be a POST, never a GET link. Escape everything per AGENTS.md. Only modify those three files.
  • Result: 8 file reads, 4 searches, then the agent stopped without writing a single file — the context-overflow symptom described in the setup guide's troubleshooting table.
  • Fix: split into three separate prompts (repository methods, POST routes, forms). The first one delivered instantly after a single file read.
  • Conclusion: small steps are a technical constraint of small context windows, not a stylistic preference.

2. The best catch (trend divergence between two pages)

Prompt

The detail page duplicates the trend logic that already exists elsewhere, and with different semantics: the list uses the position from exactly 7 days before, the detail page uses the oldest entry inside the 7-day window. Two definitions of the same rule. Fix it: 1. Add a method to src/KeywordRepository.php: positionBefore(int $keywordId, string $referenceDate): ?int — returns the position from the most recent day that is at least 7 days before the reference date, or null. 2. Use it in both branches of public/index.php, so list and detail always agree. 3. Remove the inline window/loop calculation from the keyword branch. Also: the trend_label match block is now duplicated in both branches — extract it into a small helper function in public/index.php. Only modify src/KeywordRepository.php and public/index.php.
  • Context: the detail page was functionally correct and passed every test. Reading the diff, I saw it computed the trend inline with different semantics than the list: the list required an exact date(tracked_on, '-7 days') match, the detail page took the oldest entry in the window. With fully seeded data both produce the same answer, so the bug was invisible — it would have surfaced after CRUD or after a Refresh that skipped a day, showing "Improved" on the list and "Stable" on the detail page for the same keyword.
  • Secondary defect in the same block: the loop over $history neither compared nor exited early, it only overwrote until the last matching row. It worked solely because historyFor() sorts descending; a change in sort order would have made it silently wrong.
  • Root cause: the ambiguity in my own AGENTS.md allowed both readings.
  • Result: diff of +38 −29 across two files — duplication removed, not stacked on top of.

3. Deviation from my own AGENTS.md (HTML echoed in index.php)

Prompt

Read AGENTS.md. public/index.php now handles POST actions create, update and delete (fields: action, id, phrase), and sets $error when validation fails. First: move the error rendering out of public/index.php — it currently echoes HTML there, which contradicts the "no HTML in index.php" rule. Pass $error to the view instead. Then update views/keywords_list.php: - show $error above the table when it is set - an "Add keyword" form at the top: POST, hidden action=create, a text input named phrase, a submit button - per row: an edit control (inline form with action=update, id, and the current phrase prefilled) and a delete button (POST form with action=delete and id) Delete must be POST, never a GET link. Escape every printed value, including inside attributes. Only modify public/index.php and views/keywords_list.php.
  • Context: while adding the POST routes, the agent rendered the validation error with echo directly in index.php.
  • Problem: this violated the "no HTML in index.php" rule from my own AGENTS.md. Nothing was broken — it was caught by reading the generated code, not by running it.
  • Fix: $error passed to the view and rendered there.

Testing methodology

  • XSS tested on two separate input routes: the query string (search box) and the POST form (keyword name). In both cases the payload came back escaped, and DevTools showed no <script> element in the DOM — including inside the value attribute of the edit input, which is the easiest place to miss.
  • Idempotency verified against the database, not the UI: after roughly ten consecutive AJAX Refresh clicks, SELECT COUNT(*) WHERE tracked_on = date('now') returned 9 rows for 9 keywords.
  • M7 verified by cloning the public repository into a clean directory and following the README as a first-time reader. This is how I discovered README.md was missing from the repository entirely — it had never been committed.

Section 3 — Retrospective

a) Time invested

Roughly 10 hours across five days — pre-flight and environment setup on Friday, repository scaffold and AGENTS.md on Saturday, the main build day on Sunday (schema, seed, repository, list and detail pages), CRUD, AJAX refresh and responsive CSS on Monday, README and final verification on Tuesday.

b) What I would do differently

  • Issue small prompts from the start instead of learning it from a failure.
  • Run the clean-clone test much earlier.
  • Phrase the trend rule unambiguously on day one.
  • Write session notes on the spot rather than reconstructing them.

c) Known limitations

  • PRAGMA foreign_keys is per-connection in SQLite rather than persisted in the file, so ON DELETE CASCADE depends on every connection setting it — it is set in src/Database.php, but any future entry point would need the same.
  • No automated tests (S6 not attempted).
  • Stretch goals not attempted, due to time.

d) On working with an agent

It demands the same rigour in specification as working with a junior developer. The output quality tracked directly with how precisely I bounded each request — and the one ambiguity I left in my own conventions is exactly where the code diverged.
